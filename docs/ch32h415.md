# CH32H415 platform notes

## Build

Install the WCH RISC-V toolchain and build the generic MCU target:

```sh
make SDK=ch32_sdk platform-tools-install -j128
make EXTRA_FLAGS=-Werror CH32H415 -j128
make EXTRA_FLAGS=-Werror TARGET=CH32H415 binary -j128
```

The target is registered as `ch32_sdk` in the CI target matrix. The compiler must support the `_xw` RISC-V extension used by WCH fast interrupts.

For a WCH-Link bench session without BF USB, build with
`make EXTRA_FLAGS='-Werror -DCH32H415_NO_USB' CH32H415 -j128`.
This disables the BF VCP and USB clock enable; bootloader DFU is separate.

To enable the optional BOOT-button debug handoff instead, build with
`make EXTRA_FLAGS='-Werror -DCH32H415_BOOT_SDI' CH32H415 -j128`.
The intended behavior is that BF starts with USB enabled and, after BOOT
(PC8, active high) is held for five seconds, disables the USBHS controller
and PHY and returns PB8/PB9 to the WCH-Link interface without resetting.
The handoff passed a USB-initialized bench test without a connected USB host;
see the observation below.
The USBHS peripheral clock remains enabled: in a debugger-controlled test
with USB initialization bypassed, gating it made the probe inaccessible.
The button is sampled by the 10 Hz system task, so detection can take slightly
longer than five seconds. PC8 is reserved from BF pin allocation in this build.
An ordinary reset returns to USB; holding BOOT during reset instead selects
the bootloader's DFU path. `CH32H415_BOOT_SDI` and `CH32H415_NO_USB` cannot
be enabled together. Disconnect the USB host from the shared data lines before
attaching the debug probe; use a separate power source if needed.

### RATE H4 Racing v26.9

The `RATE_H4_RACING` board configuration lives in the `src/config` submodule.
Build it with `make EXTRA_FLAGS='-Werror -DCH32H415_BOOT_SDI' RATE_H4_RACING -j128`.
It uses the board's ICM-40608 on SPI3 (PC10/PC11/PC12, CS PF3, interrupt
PA15), barometer bus I2C2 on PC0/PC1, and motors PE3 through PE6. PC9 is
connected to the IMU but is not used. PC4 and PA12 remain reserved for
the paired Theia OSD, despite their other board connections.

This board definition is based on the v26.9 schematic and netlist. The BOM
lists an ICM-42688-P, but the installed device was confirmed to be an
ICM-40608 and returned WHO_AM_I 0x39. Gyro
orientation, the actual barometer's driver compatibility, ADC calibration,
motor/LED DMA behavior and external flash operation require board-level
verification. In particular, the BOM identifies the barometer as LQTP001HTA;
including the DPS310 and BMP280 probes does not establish compatibility.
Changing from the generic CH32H415 board identifier to R4RC causes BF to
reset its stored settings to target defaults. Back up the existing settings
before the first boot of this configuration.

## Interrupt priorities

CH32 maps Betaflight's four preemption groups to IRQ priorities `0x20`, `0x60`, `0xA0` and `0xE0`. Subpriorities within a group collapse to the same value. Their atomic thresholds are `0x10`, `0x50`, `0x90` and `0xD0`: each threshold is strictly higher priority than every IRQ it must mask. IRQs never use zero; a zero threshold disables masking. This avoids relying on the PFIC threshold's equality boundary and keeps higher-priority groups available.

Use `NVIC_BUILD_PRIORITY()` for CH32 IRQ configuration, including SysTick. Atomic entry maps an IRQ priority to its group threshold; atomic exit restores the raw saved threshold without converting it again. The mapping is private to CH32 and does not change ARM priority definitions.

## Bootloader memory layout

The application layout matches the H415 bootloader contract:

- Bootloader: `0x08000000..0x08006000`
- TheiaOSD image: `0x08006000..0x0800E000`
- Font storage: `0x0800E000..0x08016000`
- V5F application: `0x08016000..0x080F0000`
- Betaflight configuration: `0x08018000`, 16 KiB
- FC SRAM starts at `0x20126000`, above the bootloader and inter-core shared areas.

`src/test/theia/check_image.py` verifies the entry point and every ELF load segment against the generated BIN. The checks do not verify electrical or runtime behavior.

The raw BIN contains padding over the configuration sectors. For an update
that preserves Betaflight settings, do not write it as one contiguous range.
Run `python3 src/utils/ch32h415_split_image.py <firmware.bin> <output-dir>`
and program the two ranges in the order and at the addresses recorded in
`manifest.json`. This avoids the configuration sectors entirely.

The paired bootloader currently enters USB DFU only through hardware BOOT0 (PC8) at reset. CH32 therefore disables `PLATFORM_SUPPORTS_SOFTWARE_BOOTLOADER`: CLI `bl` reports an error, MSP ROM/flash bootloader requests return an error, and the legacy serial reboot character is ignored. Ordinary firmware reboot remains available. Old persistent bootloader requests are cleared without selecting WCH ROM ISP. Software DFU requires an agreed application/bootloader protocol; this firmware does not add one or modify the frozen bootloader.

## TheiaOSD boundary

`USE_THEIA_OSD` selects the isolated Theia DisplayPort driver. Its shared-memory ABI v4 is private to `src/main/io/displayport_theia*`; generic MSP, CRSF and serial protocols do not carry that ABI.

The driver implements complete-screen transactions, backpressure and resync handling. Serial MSP font writes complete asynchronously and acknowledge after the OSD applies each glyph to shared RAM; the bootloader commits the font to flash on the next ordinary reset, so power loss before that reset loses the update. Requests are rejected while armed or after a timeout. MSP over telemetry does not support deferred replies and returns an error for these writes. Bootloader/Theia-owned GPIO, timers and DMA requests must not be reassigned.

Goggles-side system elements are unsupported on the analog OSD. Blink is supported; severity-specific font banks are not. Display synchronization means the current screen has been published to a ready, compatible OSD without a reported resync; it does not guarantee that pixels have already reached the video output.

For compatibility with the standard Configurator font manager, MSP reports
the internal Theia display as a MAX7456-compatible font device and reports it
detected only when the ABI, hardware-ready and OSD-running checks all pass and
OSD has consumed a recent BF heartbeat. BF probes every 250 ms, marks the
display unavailable after 1.5 seconds without an acknowledged probe, and
republishes its complete screen after recovery. A changed resync counter
invalidates a pending probe; a discarded queue is not an acknowledgement.
This checks command processing, not video signal quality or video DMA progress.
Theia stores 512 glyphs and BF accepts 16-bit glyph addresses, but the checked
Configurator font uploader sends an 8-bit address. Use at most 256 glyphs with
that uploader: a 512-glyph file would wrap the second bank onto the first.
The font write acknowledgement reports a RAM update, not flash persistence;
the bootloader's commit result is not currently exposed to Configurator.

## Verification

```sh
make EXTRA_FLAGS=-Werror checks
make EXTRA_FLAGS=-Werror test-all
make test-ch32h415 -j128
make EXTRA_FLAGS=-Werror SPEEDYBEEF405WING -j128
```

Also run the Theia producer test and the image checker after changing the driver or linker layout.

`test-ch32h415` checks actual IRQ coverage for both inclusive and strict threshold comparisons, nested atomic cleanup, and zero restore. It does not establish the PFIC's actual interrupt delivery timing on hardware.

## Validation limits

Compilation and host tests do not establish flight safety. PFIC interrupt masking, DMA ordering, UART/USB/DShot timing, flash power loss, bootloader/DFU transitions and actual TheiaOSD output require target-board validation. WCH SDK redistribution terms and maintainer acceptance must be resolved before an upstream submission.

### Bench observation, 2026-10-29

The normal H415 bootloader, Theia ABI 4 image and a BF build with
`CH32H415_NO_USB` were programmed over WCH-Link. BF's two programmed ranges
were read back byte-for-byte and the intervening configuration sectors were
unchanged. Both cores reached their running states, the ABI matched, and ring
read and write positions advanced. A temporarily enabled BF battery OSD item
was visible with a camera and with generated PAL. The item was enabled in RAM
only and does not change saved OSD settings.

With heartbeat monitoring enabled, halting the V3F OSD core for three seconds
made BF mark the display offline even though the boot-state word remained
RUNNING. Resuming V3F restored the online state and the ring drained again.
This tested the internal health state, not an MSP response over a serial port.

The generic target's observed ADC DMA options were unset, so this observation
does not validate battery voltage measurement. Board-specific ADC pins and
DMA allocation still need configuration and electrical verification. Serial
MSP font upload, reboot-time font persistence, USB/DFU, and flight peripherals
were not exercised in this bench session.

### BOOT-button USB/debug handoff observation, 2026-10-29

The opt-in `CH32H415_BOOT_SDI` image was flashed in two ranges; both ranges
were read back byte-for-byte. After starting the USB-enabled firmware,
WCH-Link reported protocol error `0x55` while attempting to attach. The user
held BOOT for about six seconds and released it; WCH-Link still reported the
same error. The initial implementation and the subsequent version retaining
the USBHS peripheral clock both showed this failure. USB enumeration was not
verified, and the cause of the failed real handoff remains undetermined.

With both cores halted early at a later power-on, PC8 read low when BOOT was
released and high when it was pressed. In a separate debugger-controlled test,
temporarily bypassing USB initialization in RAM left the debug link accessible;
BF initialized the button task and a simulated press reached the handoff
function after about 5.1 seconds. In this modified execution, gating the
USBHS peripheral clock was followed by loss of debug access. On a later run,
skipping that clock-gating call allowed the subsequent UTMI disable and SWJ
remap calls to complete while debug access remained available. These modified
executions do not prove that handoff works after normal USB initialization.
Temporary RAM patches and the hardware breakpoint were removed before the
second image was flashed.

A subsequent instrumented run displayed BF execution state via the independent
Theia core. With USB initialization enabled and no USB host cable connected,
the system task continued running, the physical BOOT press was detected, and
the handoff returned from USB deinitialization and reached the SWJ remap.
Readback showed SW_CFG=0, USB CONTROL=0, INT_EN=0, and the UTMI clock gated,
but WCH-Link still failed to attach. PB8 remained an open-drain output from
the USB disconnect pulse; changing it to floating input did not restore attach.
Holding the USB LINK and SIE in reset and clearing USB state (CONTROL=0x07)
did restore attach. Returning PB8 to its previous configuration did not lose
the connection. The individual reset bits were not isolated.

The revised BF handoff writes CONTROL=0x07. In a normal USB-initialized
instrumented boot, a physical BOOT hold reached the handoff with PB8 still in
its original configuration and WCH-Link attached successfully. After replacing
both diagnostic images with the normal OSD image and the non-instrumented BF
build, WCH-Link again failed before the BOOT hold and attached successfully
after it. BF configuration readback matched before and after this final boot
and hold. This verifies the handoff on the bench; USB enumeration with a host
and flight operation were not tested.

The 16 KiB BF configuration contents differed between the readbacks taken
before and after the intervening power cycles and debug sessions. The exact
event causing the change has not been established. Both versions and the
original full Flash backup are retained in the bench artifacts; do not infer
configuration preservation across these sessions from the split flash ranges.
