# CH32H415 platform notes

## Build

Install the WCH RISC-V toolchain and build the generic MCU target:

```sh
make SDK=ch32_sdk platform-tools-install -j128
make EXTRA_FLAGS=-Werror CH32H415 -j128
make EXTRA_FLAGS=-Werror TARGET=CH32H415 binary -j128
```

The target is registered as `ch32_sdk` in the CI target matrix. The compiler must support the `_xw` RISC-V extension used by WCH fast interrupts.

For a WCH-Link bench session without BF USB, build with
`make EXTRA_FLAGS='-Werror -DCH32H415_NO_USB' CH32H415 -j128`.
This disables the BF VCP and USB clock enable; bootloader DFU is separate.

## Interrupt priorities

CH32 maps Betaflight's four preemption groups to IRQ priorities `0x20`, `0x60`, `0xA0` and `0xE0`. Subpriorities within a group collapse to the same value. Their atomic thresholds are `0x10`, `0x50`, `0x90` and `0xD0`: each threshold is strictly higher priority than every IRQ it must mask. IRQs never use zero; a zero threshold disables masking. This avoids relying on the PFIC threshold's equality boundary and keeps higher-priority groups available.

Use `NVIC_BUILD_PRIORITY()` for CH32 IRQ configuration, including SysTick. Atomic entry maps an IRQ priority to its group threshold; atomic exit restores the raw saved threshold without converting it again. The mapping is private to CH32 and does not change ARM priority definitions.

## Bootloader memory layout

The application layout matches the H415 bootloader contract:

- Bootloader: `0x08000000..0x08006000`
- TheiaOSD image: `0x08006000..0x0800E000`
- Font storage: `0x0800E000..0x08016000`
- V5F application: `0x08016000..0x080F0000`
- Betaflight configuration: `0x08018000`, 16 KiB
- FC SRAM starts at `0x20126000`, above the bootloader and inter-core shared areas.

`src/test/theia/check_image.py` verifies the entry point and every ELF load segment against the generated BIN. The checks do not verify electrical or runtime behavior.

The raw BIN contains padding over the configuration sectors. For an update
that preserves Betaflight settings, do not write it as one contiguous range.
Run `python3 src/utils/ch32h415_split_image.py <firmware.bin> <output-dir>`
and program the two ranges in the order and at the addresses recorded in
`manifest.json`. This avoids the configuration sectors entirely.

The paired bootloader currently enters USB DFU only through hardware BOOT0 (PC8) at reset. CH32 therefore disables `PLATFORM_SUPPORTS_SOFTWARE_BOOTLOADER`: CLI `bl` reports an error, MSP ROM/flash bootloader requests return an error, and the legacy serial reboot character is ignored. Ordinary firmware reboot remains available. Old persistent bootloader requests are cleared without selecting WCH ROM ISP. Software DFU requires an agreed application/bootloader protocol; this firmware does not add one or modify the frozen bootloader.

## TheiaOSD boundary

`USE_THEIA_OSD` selects the isolated Theia DisplayPort driver. Its shared-memory ABI v4 is private to `src/main/io/displayport_theia*`; generic MSP, CRSF and serial protocols do not carry that ABI.

The driver implements complete-screen transactions, backpressure and resync handling. Serial MSP font writes complete asynchronously and acknowledge after the OSD applies each glyph to shared RAM; the bootloader commits the font to flash on the next ordinary reset, so power loss before that reset loses the update. Requests are rejected while armed or after a timeout. MSP over telemetry does not support deferred replies and returns an error for these writes. Bootloader/Theia-owned GPIO, timers and DMA requests must not be reassigned.

Goggles-side system elements are unsupported on the analog OSD. Blink is supported; severity-specific font banks are not. Display synchronization means the current screen has been published to a ready, compatible OSD without a reported resync; it does not guarantee that pixels have already reached the video output.

For compatibility with the standard Configurator font manager, MSP reports
the internal Theia display as a MAX7456-compatible font device and reports it
detected only when the ABI, hardware-ready and OSD-running checks all pass.
Theia stores 512 glyphs and BF accepts 16-bit glyph addresses, but the checked
Configurator font uploader sends an 8-bit address. Use at most 256 glyphs with
that uploader: a 512-glyph file would wrap the second bank onto the first.
The font write acknowledgement reports a RAM update, not flash persistence;
the bootloader's commit result is not currently exposed to Configurator.

## Verification

```sh
make EXTRA_FLAGS=-Werror checks
make EXTRA_FLAGS=-Werror test-all
make test-ch32h415 -j128
make EXTRA_FLAGS=-Werror SPEEDYBEEF405WING -j128
```

Also run the Theia producer test and the image checker after changing the driver or linker layout.

`test-ch32h415` checks actual IRQ coverage for both inclusive and strict threshold comparisons, nested atomic cleanup, and zero restore. It does not establish the PFIC's actual interrupt delivery timing on hardware.

## Validation limits

Compilation and host tests do not establish flight safety. PFIC interrupt masking, DMA ordering, UART/USB/DShot timing, flash power loss, bootloader/DFU transitions and actual TheiaOSD output require target-board validation. WCH SDK redistribution terms and maintainer acceptance must be resolved before an upstream submission.

### Bench observation, 2026-10-29

The normal H415 bootloader, Theia ABI 4 image and a BF build with
`CH32H415_NO_USB` were programmed over WCH-Link. BF's two programmed ranges
were read back byte-for-byte and the intervening configuration sectors were
unchanged. Both cores reached their running states, the ABI matched, and ring
read and write positions advanced. A temporarily enabled BF battery OSD item
was visible with a camera and with generated PAL. The item was enabled in RAM
only and does not change saved OSD settings.

The generic target's observed ADC DMA options were unset, so this observation
does not validate battery voltage measurement. Board-specific ADC pins and
DMA allocation still need configuration and electrical verification. Serial
MSP font upload, reboot-time font persistence, USB/DFU, and flight peripherals
were not exercised in this bench session.
